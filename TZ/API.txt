Умная диспетчеризация выездных бригад — API решения
 1.0.0 
OAS 3.0
Единый формат REST API, который реализует каждая команда в кейсе «Умная диспетчеризация выездных бригад» (Всероссийский хакатон связи 2026, ПАО «Ростелеком»).

По этому API оркестратор организаторов загружает данные, получает план смены, передаёт события в течение дня и забирает актуальный план. Валидатор организаторов пересчитывает каждый план по единой матрице времени в пути и считает метрики. Отклонение от формата (имена полей, типы, коды HTTP) приводит к тому, что план не будет оценён.

1. Сценарий оценки одного дня
Шаг	Вызов	Лимит
1	GET /api/v1/health — ждём 200 после docker compose up	120 с с момента старта
2	PUT /api/v1/reference — СЦ, сотрудники, узлы доступа с домами, типы работ	60 с
3	PUT /api/v1/reference/travel-matrix — единая матрица времени в пути	60 с
4	PUT /api/v1/days/{date} — наряды дня, известные на момент now	30 с
5	POST /api/v1/days/{date}/plan — построение плана	300 с
6	для каждого события по возрастанию timestamp: POST /api/v1/days/{date}/events, затем GET /api/v1/days/{date}/plan	10 с на событие
7	итоговый GET /api/v1/days/{date}/plan — по нему считаются метрики	30 с
Шаги 2–3 выполняются один раз за прогон, шаги 4–7 — для каждого из оцениваемых дней. Загрузка нового дня может удалять состояние предыдущего: сервис обязан держать как минимум один активный день.

2. Модельное время
Сервис не использует системные часы. Текущее модельное время — это now из загрузки дня, а после событий — timestamp последнего принятого события.

Моменты времени — ISO 8601 со смещением: 2026-10-26T09:00:00+05:00 (Екатеринбург, UTC+5). Сервис принимает любое корректное смещение, в ответах рекомендуется +05:00.
Время суток в справочниках (смены, режим работы СЦ) — местное, формат HH:MM.
Точность — секунды. Допуск валидатора при сравнении времени — 1 с.
Длительности — в минутах (*_min) или секундах (*_sec), расстояния — в метрах (*_m).
3. Модель исполнения плана
Оркестратор считает, что сотрудники выполняют текущую версию плана в точности, а все отклонения приходят событиями. Поэтому выполненную часть плана менять нельзя. В момент модельного времени t:

остановка с start < t считается начатой: в следующих версиях плана у неё нельзя менять сотрудника, наряд, location_id, arrival и start; end меняется только по событиям VISIT_DELAYED и ORDER_TRANSFERRED;
если у остановки изменился предшественник в маршруте или она новая, то arrival ≥ max(end предшественника, t) + время в пути — сотрудник не может оказаться у нового адреса раньше, чем узнал о нём;
визит по наряду из события NEW_ORDER начинается не раньше timestamp события;
отменённый наряд (ORDER_CANCELLED) не посещается, если визит ещё не начат;
у сотрудника из события STAFF_UNAVAILABLE не может быть остановок, начинающихся в период недоступности. Визит, начатый до timestamp события, считается выполненным по плану.
4. Жёсткие ограничения
Валидатор проверяет каждую версию плана. Наряд, на котором нарушено ограничение, не засчитывается и даёт штраф (п. 6 кейса).

Код	Ограничение
H1 Допуск	хотя бы один профиль сотрудника входит в work_type.profiles; order.technology входит в staff.technologies; при order.requires_height = true нужен staff.height_permit = true
H2 Смена	DEPOT_START.start ≥ shift.start; DEPOT_END.arrival ≤ shift.end; все остановки — внутри смены
H3 Перерыв	если в маршруте есть визиты — ровно одна остановка BREAK длительностью не меньше shift.break_duration_min, start внутри [break_window.from, break_window.to]; перерыв не пересекается с другими остановками
H4 Слот	order.slot.start ≤ VISIT.start ≤ order.latest_start
H5 Норматив	VISIT.end − VISIT.start = work_type.duration_min (или момент из события VISIT_DELAYED / ORDER_TRANSFERRED)
H6 Дорога	arrival(k) ≥ end(k−1) + travel(location(k−1), location(k)) по единой матрице; start ≥ arrival; end ≥ start
H7 АО	остаток в «рюкзаке» моделируется по маршруту: старт — staff.equipment_start; визит списывает order.required_equipment в момент start, остаток не может стать отрицательным; RESTOCK доводит остаток до staff.equipment_capacity
H8 СЦ	DEPOT_START и DEPOT_END — в СЦ сотрудника (staff.service_center_id); RESTOCK — в любом СЦ, открытом на всём интервале [start, end], длительность не меньше restock_duration_min
H9 Учёт	каждый наряд дня (из загрузки и из NEW_ORDER) находится ровно в одном месте: визит в маршруте, unassigned, pgp_groups[].order_ids или cancelled
H10 Заморозка	правила раздела 3 между последовательными версиями плана
Ограничения по типам остановок: первая остановка маршрута — DEPOT_START, последняя — DEPOT_END (у недоступного сотрудника DEPOT_END не обязателен); у VISIT location_id = order.building_id; у BREAK location_id совпадает с предыдущей остановкой, время в пути до перерыва равно 0.

5. Как план используется в оценке
Наряд выполнен успешно, если визит начат в окне [slot.start, latest_start], завершён не позднее deadline и не нарушает H1–H10. Повторные обращения (is_repeat = true) идут с весом 2. Генератор данных гарантирует, что latest_start + duration_min ≤ deadline.
Время в пути и загрузка считаются по итоговой версии плана и единой матрице. Значения travel_sec, distance_m, totals, summary в ответе — справочные, валидатор их пересчитывает.
Предупреждение о риске опоздания своевременно, если Alert типа LATE_RISK по наряду создан (created_at) не позднее чем за 30 минут до slot.start. Оценивается по нарядам, которые после событий были переназначены другому сотруднику или сняты из маршрута.
ПГП: группы pgp_groups сравниваются с эталонными инцидентами по составу нарядов (точность и полнота) и по моменту detected_at.
Время ответа: план дольше 300 с — день не оценивается автоматически; событие дольше 10 с считается необработанным в срок.
6. Файлы исходных данных
Файлы из п. 4 кейса описаны схемами *File. Все JSON — UTF-8, корневой элемент — массив (кроме travel_matrix.json и файлов сценария событий).

Файл	Схема	Куда передаётся
service_centers.json	ServiceCentersFile	PUT /reference → service_centers
staff.json	StaffFile	PUT /reference → staff
access_nodes.json	AccessNodesFile	PUT /reference → access_nodes
work_types.csv	WorkType (строка CSV)	PUT /reference → work_types
travel_matrix.json	TravelMatrix	PUT /reference/travel-matrix
orders_train.json	OrdersFile	PUT /days/{date} → orders (наряды со слотом в этот день и registered_at ≤ now)
events_example.json	EventScenarioFile	events → POST /events; triggers разворачивает оркестратор
work_types.csv — RFC 4180, разделитель запятая, UTF-8 без BOM, первая строка — заголовок с именами полей схемы WorkType; списки (profiles) записываются через |, пустое значение — null.

7. Общие соглашения
Базовый путь /api/v1, порт по умолчанию 8080, тело запросов и ответов — application/json. Сервис принимает тела до 100 МБ (матрица времени в пути — около 20 МБ).
Идентификаторы — строки, регистр значим. Значения перечислений — строго как в спецификации.
Сервис игнорирует неизвестные поля во входных данных (например, fact в обучающих нарядах). В ответах допускаются дополнительные поля, валидатор их не читает; обязательные поля и типы — строго.
Ошибки возвращаются в формате ErrorResponse; при ошибке состояние сервиса не меняется.
Дополнительные эндпоинты (UI, сценарный анализ, объяснения) допускаются под любыми другими путями.
Авторизация не требуется.
