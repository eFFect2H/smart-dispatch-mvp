Отчёт: smart-dispatch-mvp и доработка под кейс «Умная диспетчеризация»
Документ подготовлен по архиву smart-dispatch-mvp-master.zip и PDF кейса Ростелекома. Код я прочитал целиком, но проект не собирал и не запускал (нет JDK/Docker в моей среде), поэтому выводы основаны на статическом анализе. Файлов организаторов (api_spec.yaml, staff.json, orders_train.json и др.) у меня нет, их формат ниже описан по PDF.
1. Главный вывод
Проект — универсальный каркас VRPTW: Java 21, Spring Boot 3.5, PostgreSQL + Flyway, OR-Tools, OSRM, React + Leaflet. Данные демо — Берлин, сущности — «бригады» и «транспортные заявки». Предметной области кейса (наряды, допуски, АО, слоты, 3ЛТП, ПГП, события) в нём нет, а самое важное — модель оптимизации — устроена так, что без переписывания в неё эти правила не добавить.
Что полезно оставить: стек (Java разрешена кейсом), БД с миграциями, OSRM-клиент, готовую карту Leaflet и каркас страниц React. Оценка: бэкенд оптимизации придётся переписать примерно на 70%, интерфейс переработать на 50-60%.
2. Что реализовано сейчас
•	CRUD бригад и заявок (/api/teams, /api/requests), миграции и демо-данные.
•	POST /api/dispatch/optimize: матрица времени из OSRM, VRPTW в OR-Tools (окна, смены, вместимость), геометрия маршрутов из OSRM, сохранение назначений.
•	Интерфейс: страницы «Обзор», «Заявки», «Бригады», «Диспетчеризация» (карта + карточки маршрутов).

3.2 Серьёзные (теряются баллы за качество плана)
•	Слот и правило «+10 минут». Окно — произвольный интервал, нет двухчасового слота и нет отдельного правила для инсталляции (не позднее 10 минут после начала слота).
•	Нет смены, обеда, СЦ. Бригада стартует и заканчивает в своей «стартовой точке», а не в СЦ. Нет смен 12:00-21:00 как отдельной сущности, нет перерыва на час.
•	Нет типов работ и нормативов. Длительность вводится вручную, нет справочника из work_types.csv.
•	Нет контрольных сроков и дат. Всё в минутах от полуночи: нельзя выразить 24 часа, 12 часов для повторных, 3 и 5 рабочих дней.
•	Нет повторных обращений и весов. Единственная цель — время в пути.
•	Нет цели равномерной загрузки и счёта переносов.
•	Нет раннего предупреждения о риске опоздания.
•	Сотрудник и бригада. В кейсе работают отдельные сотрудники (40 человек), в проекте — «бригады» с вместимостью. Совместные наряды (два человека на ВЛС) в такой модели не выразить.
3.3 Технические дефекты
•	Конфликт настроек БД. application.properties жёстко задаёт 127.0.0.1:5432, пользователя postgres и пароль 521340, а docker-compose.yml поднимает БД на порту 5433 с пользователем dispatch. README обещает переменные DB_URL, DB_USERNAME, DB_PASSWORD, но в properties они не используются. По README проект не стартует. Пароль нужно убрать из репозитория.
•	README ссылается на Maven Wrapper, которого в архиве нет.
•	Тестов нет (нет каталога src/test), хотя spring-boot-starter-test подключён.
•	Публичный OSRM router.project-osrm.org — без SLA, лимиты, зависимость от интернета. Для проекта нужен собственный OSRM на данных Уральского ФО.
•	Нет блокировки параллельных расчётов: два одновременных optimize перезапишут друг другу назначения.
•	Демо-данные по Берлину, а адреса — «Potsdamer Platz» и т.п.

6. Как сделать интерфейс понятнее
Сейчас интерфейс — классическая админка (4 страницы, карточки, формы). Для диспетчера это неудобно: чтобы увидеть результат, надо перейти на «Диспетчеризацию» и нажать кнопку, а смотреть приходится по карточкам.
6.1 Структура
1.	Один главный рабочий экран вместо четырёх страниц: слева карта, справа сверху диаграмма Ганта, справа снизу списки. «Заявки» и «Бригады» остаются как справочные экраны.
2.	Связать всё между собой: клик по строке списка, полосе Ганта или точке на карте подсвечивает наряд везде и показывает карточку сбоку.
3.	Вертикальная линия «сейчас» на диаграмме и ползунок времени для просмотра плана на другой момент.
6.2 Списки, с которыми диспетчер реально работает
•	Нераспределённые: причина простыми словами («нет допуска на высоту», «не хватает времени смены», «нет ONT в рюкзаках») и кнопка действия рядом.
•	С риском опоздания: запас в минутах, цветовая шкала, кнопки «Предложить перенос» и «Передать другому» с выбором сотрудника.
•	ПГП: группа нарядов под одним узлом, одна кнопка «Передать в станционное подразделение».
•	Фильтры по СЦ, профилю, технологии, статусу.
6.3 События и перепланирование
•	Панель «Событие» на экране: задержка на объекте, абонент не подтвердил, сотрудник недоступен, новый наряд.
•	После пересчёта показывать что изменилось («3 наряда переназначены, 1 выпал из плана») и подсветить изменения, а не молча заменять план.
•	Явный индикатор состояния («Идёт расчёт, до 6 с»), а не блокировка экрана.
6.4 Ввод данных
•	Форма наряда: тип работ выбирается из списка, норматив и профиль подставляются сами; слот — выпадающий список двухчасовых интервалов, а не два свободных поля времени.
•	Адрес и координаты: сейчас широта и долгота вводятся руками. Лучше: поиск адреса или клик по карте.
•	Массовая загрузка JSON/CSV кнопкой «Загрузить данные».
6.5 Язык и вид
•	Единая терминология кейса: наряд, сотрудник, СЦ (сейчас «заявка», «бригада», «транспортная заявка»).
•	Время везде в формате ЧЧ:ММ, длительности «1 ч 20 мин».
•	Цвет несёт смысл и одинаков везде: инсталляция и неисправность разными тонами, риск и нераспределённый — красным, ПГП — отдельным цветом. Не полагаться только на цвет (добавить значки и подписи).
•	Пустые состояния должны подсказывать действие («Загрузите данные и нажмите “Построить план”»).
•	Карта: маршрут по дорожной сети (геометрия уже есть), номера остановок, стрелки направления, кластеризация при 400 точках.
6.6 Объяснимость
По клику на наряд короткий блок «Почему назначен этому сотруднику»: допуск подходит, ближайший по времени, есть АО, влезает в слот. Это и доп. задание кейса, и экспертные баллы за наглядность.

8. Решение: на чём строить
Есть две дороги, и выбор зависит от команды.
•	Остаться на этом проекте (Java + React). Плюс: уже есть БД, миграции, OSRM-клиент и интерфейс с картой. Минус: оптимизатор по сути пишется заново, но модель из Python-прототипа переносится почти строка в строку на Java OR-Tools.
•	Взять мой Python-прототип (FastAPI + OR-Tools, уже работает на тестовых данных, события и ПГП есть). Плюс: быстрее до результата. Минус: нет БД и мало интерфейса, всё хранится в памяти.
Рекомендация: если команда уверенно пишет на Java, остаться на этом проекте и портировать модель; если нет, взять Python-прототип и перенести в него полезное отсюда (Postgres, миграции, React-карту). Смешивать два бэкенда не стоит.
9. Ограничения этого отчёта
•	Проект не собирался и не запускался, поведение выведено из кода.
•	Формат api_spec.yaml неизвестен, поэтому раздел про API — предположение.
•	Оценки часов ориентировочные и зависят от опыта команды.
