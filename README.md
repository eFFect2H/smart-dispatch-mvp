# Smart Dispatch MVP

Минимальный backend для кейса «Умная диспетчеризация выездных бригад».

## Что уже реализовано

- REST API для чтения и создания бригад и транспортных заявок.
- PostgreSQL и миграции схемы/демо-данных через Flyway.
- Матрица автомобильного времени между базами бригад и заявками через OSRM Table API.
- Оптимизация назначений и порядка посещения через Google OR-Tools (VRPTW): временные окна, смены бригад, длительность обслуживания и суммарная вместимость.
- Сохранение рассчитанных назначений и планового времени прибытия в PostgreSQL.
- Примерные данные по Берлину применяются автоматически при первом запуске пустой БД.

## Требования

- JDK 21.
- Docker Desktop с Docker Compose (или доступный локальный PostgreSQL 16).
- Подключение к интернету для публичного демо-сервера OSRM `router.project-osrm.org`.
- Maven Wrapper из проекта Initializr или Maven 3.6.3+.

Публичный OSRM используется только для разработки/демонстрации и не гарантирует SLA. Для нормальной эксплуатации настройте собственный или управляемый сервер маршрутизации через `OSRM_BASE_URL`.

## Запуск

1. Распакуйте архив и откройте папку `smart-dispatch-mvp` в IntelliJ IDEA как Maven-проект.
2. Запустите PostgreSQL:

   ```bash
   docker compose up -d db
   ```

3. Убедитесь, что используется JDK 21 (`File → Project Structure → Project SDK`).
4. Запустите `SmartDispatchApplication.java` или из терминала выполните:

   ```bash
   mvn spring-boot:run
   ```

   В IntelliJ IDEA можно запустить `spring-boot:run` из окна Maven (`Plugins → spring-boot → spring-boot:run`). Если Maven установлен, команда в терминале: `mvn spring-boot:run`.

5. При первом старте Flyway создаст таблицы и добавит 2 тестовые бригады и 5 заявок.

Настройки подключения к PostgreSQL задаются переменными окружения `DB_URL`, `DB_USERNAME` и `DB_PASSWORD`. Для локального PostgreSQL можно использовать порт `5432`; для контейнера из `docker-compose.yml` — порт хоста `5433` и пользователя `dispatch`. Пароль передавайте через `DB_PASSWORD`, не записывая его в исходный код.

## API

### Получить бригады

```http
GET http://localhost:8080/api/teams
```

### Создать бригаду

```http
POST http://localhost:8080/api/teams
Content-Type: application/json

{
  "name": "Южная бригада",
  "capacity": 3,
  "startLatitude": 52.49,
  "startLongitude": 13.40,
  "shiftStartMinute": 480,
  "shiftEndMinute": 1080,
  "active": true
}
```

### Получить заявки

```http
GET http://localhost:8080/api/requests
```

### Создать заявку

Временные значения передаются в минутах от полуночи: `480` = 08:00, `615` = 10:15. Временное окно ограничивает время начала обслуживания.

```http
POST http://localhost:8080/api/requests
Content-Type: application/json

{
  "title": "Срочный вызов",
  "address": "Potsdamer Platz, Berlin",
  "latitude": 52.5096,
  "longitude": 13.3759,
  "windowStartMinute": 600,
  "windowEndMinute": 720,
  "serviceDurationMinutes": 30,
  "demand": 1
}
```

### Рассчитать диспетчеризацию

```http
POST http://localhost:8080/api/dispatch/optimize
```

Тело запроса не требуется. В ответе будут маршруты по каждой активной бригаде, порядок заявок, оценка времени прибытия, время в пути и суммарное время движения. Результат также сохраняется: заявки переходят в `PLANNED`, получают `assignedTeamId` и `plannedArrivalMinute`.

Для повторного расчёта берутся заявки со статусами `NEW` и `PLANNED`; завершённые (`COMPLETED`) не участвуют. На данном этапе отдельного API для завершения заявки ещё нет.

### Повторить запросы из PowerShell

```powershell
Invoke-RestMethod http://localhost:8080/api/teams
Invoke-RestMethod http://localhost:8080/api/requests
Invoke-RestMethod -Method Post http://localhost:8080/api/dispatch/optimize
```

## Архитектура

- `controller/` — REST endpoints.
- `dto/` — модели HTTP-запросов и ответов.
- `entity/` — JPA-сущности.
- `repository/` — доступ к PostgreSQL через Spring Data JPA.
- `service/` — бизнес-логика и транзакции.
- `routing/OsrmMatrixClient` — матрица времени в пути из OSRM.
- `optimization/DispatchOptimizerService` — построение модели и решение VRPTW в OR-Tools.
- `resources/db/migration/` — SQL-миграции Flyway.

## Ограничения MVP

- Все заявки должны быть распределены; если задача не имеет допустимого решения с заданными окнами/вместимостью/сменами, API возвращает HTTP 422.
- `capacity` и `demand` — абстрактные единицы вместимости, пока не разделённые на людей, оборудование или тип транспорта.
- Нет учёта навыков бригад, перерывов, пробок в реальном времени, приоритетов, стоимости сверхурочных, ручного закрепления и отмены заявок.
- Время в ответе — минуты от полуночи, а не форматированная локальная дата/время.
- Матрица ограничена 100 точками в этом MVP.
- Интерфейс-карта, аутентификация и управление завершёнными заявками — следующие итерации, не часть этого начального backend MVP.


## API организатора v1 — Stage A

Поддерживаемый контур загрузки исходных данных расположен отдельно от legacy API:

- `GET /api/v1/health` — проверка готовности сервиса.
- `PUT /api/v1/reference` — загрузка справочников.
- `PUT /api/v1/reference/travel-matrix` — загрузка единой матрицы времени и расстояний.
- `PUT /api/v1/days/{date}` — загрузка входных данных конкретного дня.

Справочники, матрица и входные данные дня сохраняются как JSONB-снимки. Для матрицы дополнительно проверяется квадратность обеих матриц, уникальность точек, нулевые диагональные значения и соответствие точек всем СЦ и домам из справочников, если справочники уже загружены. Матрица может быть отправлена до или после справочников.

Загрузка справочников удаляет ранее загруженное состояние дней. Все операции записи транзакционные. Модельное время берётся из поля `now` запроса дня; системное время не используется при проверке временных ограничений нарядов.

Для локального PostgreSQL задайте переменные окружения `DB_URL`, `DB_USERNAME` и `DB_PASSWORD`. Для Docker Compose из этого репозитория используйте порт хоста `5433`, пользователя `dispatch` и пароль `dispatch`. Пароли и другие секреты не следует коммитить в `application.properties`.


## Stage B1 — базовое планирование V1

Ветка `feature/stage-b1-planning-api` добавляет:

- `POST /api/v1/days/{date}/plan` — формирование и сохранение следующей версии плана;
- `GET /api/v1/days/{date}/plan` — получение последнего сохранённого плана;
- хранение `plan_version`, `plan_payload` и `plan_as_of` в записи дня;
- базовое последовательное распределение заказов по сотрудникам с учётом профиля, технологии, допуска к высотным работам, смены, временного окна и нормативной длительности;
- расчёт времени и расстояния исключительно по загруженной `travel_matrix`.

B1 использует детерминированную жадную эвристику: заказы сортируются по началу слота, затем выбирается допустимый сотрудник с минимальной суммой времени до заказа и возврата в свой СЦ. Это базовый планировщик, а не полноценный VRPTW solver.

**Ограничения, которые остаются на следующие этапы:** обязательный перерыв (H3), оборудование и RESTOCK (H7–H8), PGP-группы и alerts, а также заморозка исполненных остановок при обработке событий (H10). В B1 соответствующие коллекции ответа возвращаются пустыми. Не следует считать этот этап полной реализацией всех ограничений API.


## Stage B2 — жёсткие ограничения маршрута

B2 расширяет V1-планировщик проверками H3, H7 и H8:

- обязательный единственный `BREAK` для каждого маршрута с визитами; перерыв вставляется в одну из позиций маршрута, остаётся на локации предыдущей остановки и начинается внутри `break_window`;
- учёт остатка `ONT`, `ROUTER`, `STB` от `equipment_start`; каждый визит списывает требуемое оборудование;
- при нехватке оборудования планировщик пробует добавить `RESTOCK` в доступном сервисном центре; после него запас доводится до `equipment_capacity`;
- интервал `RESTOCK` должен целиком находиться внутри часов работы выбранного СЦ и иметь длительность не меньше `restock_duration_min`;
- в `equipment_after` каждой остановки возвращается остаток оборудования после её выполнения.

При добавлении каждого наряда пересчитывается весь ещё не исполненный маршрут: расписание должно одновременно сохранять окна визитов, нормативы, дорогу по входной матрице, перерыв, пополнение и возврат в СЦ в пределах смены.

B2 по-прежнему использует детерминированную эвристику последовательного добавления, а не глобально оптимальный VRPTW solver. PGP-группы, LATE_RISK alerts и обработка/заморозка событий остаются за пределами B2.


## Stage B3 — контроль целостности и качество плана

B3 добавляет финальную обработку первоначального плана:

- выявление ПГП по `work_type.pgp_relevant`: не менее трёх нарядов одного узла доступа в скользящем 60-минутном окне; такие наряды попадают в `pgp_groups` и не назначаются индивидуально;
- создание предупреждений `PGP_DETECTED` и `UNASSIGNED` с модельным временем;
- контроль H1–H8 валидатором готового маршрута до сохранения плана;
- контроль H9: каждый входной наряд находится ровно в одном месте — VISIT, `unassigned`, `pgp_groups` или `cancelled`;
- по одному маршруту на каждого сотрудника, включая пустые маршруты;
- расчёт `RouteTotals`: визиты, время/расстояние в пути, нормативное рабочее время и utilization;
- расчёт `PlanSummary`: общее число нарядов, распределённые, нераспределённые и ПГП-наряды, отмены, суммарное время в пути и коэффициент вариации загрузки.

ПГП определяется при первоначальном построении плана. Перенос уже начатых визитов, обновление предупреждений событиями и H10 freeze остаются этапом C.


## Stage C1 — журнал событий дня

C1 добавляет append-only журнал событий отдельно от входного снимка дня и сохранённого плана:

- POST /api/v1/days/{date}/events — принять одно событие;
- GET /api/v1/days/{date}/events — получить историю в порядке сохранения;
- миграция V5 создаёт v1_dispatch_events с уникальностью (day_date, event_id), последовательностью приёма, временем события и JSONB payload;
- повторная отправка того же event_id с тем же содержимым идемпотентна; повторное использование ID с другим содержимым возвращает конфликт;
- occurred_at должен относиться к дате из URL и не может быть раньше текущего model_now; после записи модельное время дня продвигается до времени события;
- замена входного снимка через PUT /api/v1/days/{date} очищает историю событий этого дня, так как события относятся к конкретному базовому снимку.

Поддерживаемые типы: NEW_ORDER, ORDER_CANCELLED, VISIT_DELAYED, STAFF_UNAVAILABLE, ORDER_TRANSFERRED.

Для VISIT_DELAYED поле payload.delay_min должно быть положительным целым числом. Для STAFF_UNAVAILABLE требуется staff_id; для ORDER_TRANSFERRED — order_id и target_staff_id. NEW_ORDER требует order_id и объект payload.order, соответствующий схеме OrderDto; его order_id, registered_at и slot.start сверяются с оболочкой события и датой.

C1 сохраняет и проверяет события, но ещё не перестраивает маршруты и не применяет H10 freeze. После записи ответ имеет статус RECORDED_PENDING_REPLAN; сохранённый план остаётся последним рассчитанным планом. Динамическая обработка событий и пересчёт планов относятся к следующим подэтапам Stage C.
